# Audit of the poll bot

Done by running the real bot against a fake Slack and a fake database (`sim/`,
exercised by `test-sim.js`) and by reading the code. Everything under
**Confirmed by running it** has a `todo` test in `test-sim.js` that reproduces it;
fix the bug, delete the `todo` option, and the test becomes a guard.

Ranked by what it costs a person, not by how hard it is to fix.

## Confirmed by running it

### 1. A poll can ping the whole channel, and carry a disguised link (high)
Poll titles, descriptions, questions and options go into Slack messages as-is.
Slack treats `<!channel>`, `<!here>` and `<!everyone>` as pings, `<@U123>` as a
mention, and `<https://evil.example|Sign in>` as a link whose visible text is
whatever the writer likes. Anyone who can run `/newpoll` can therefore make the
bot send an `@channel` to every room it posts in, under the bot's name, ten times
a day (the creation limit), and can post a phishing link in a message that looks
official.

Slack's rule for untrusted text is to escape `&`, `<` and `>` as `&amp;`, `&lt;`
and `&gt;`. That belongs in one place, where poll text becomes message text
(`pollDisplayTitle`, `questionText`, option text and the `text:` fallbacks), not
at each call site. Test: *a poll cannot ping the whole channel…* and *…carry a
link whose visible text hides its destination*.

### 2. The message can show an older tally than the database (medium)
Every vote refreshes the poll message from the poll *it* just wrote. If two votes
land close together and their refreshes arrive out of order, the older tally
overwrites the newer one and stays until the next vote. Reproduced: the database
holds 2 votes, the message says 1 participant. Quiet polls, where the last vote
is the one that gets lost, are the worst case, because nothing corrects it.

Fix: have `updatePollMessage` read the poll fresh from the database immediately
before it posts (cheap), or coalesce refreshes per poll so only the latest wins.
Coalescing also helps with Slack's own limit on message updates, which the bot
currently meets by ignoring failures (`Promise.allSettled`), so a rate-limited
refresh would silently leave a stale message (not reproduced here: the fake does
not model Slack's rate limits). Test: *the message tally always matches
the database…*.

### 3. A poll with an NPS question can never be posted (high)
NPS has eleven choices (0 to 10). The limit is ten. The creator fills in the
form, presses Post, the form closes, and then a DM says *"Question 1: exceeds
maximum number of options (10)"*. The README advertises NPS. Nothing in the unit
tests passes a built question through the same validation the post path uses,
which is why 380 tests missed it. Test: *a poll with an NPS question can be
posted*.

Fix: the limit exists to bound what people type; the fixed scales (NPS, 1 to 10,
agree/disagree) are generated by the bot, so exempt them, or raise the limit to
eleven. Either way, add a test that every question type survives
`validatePollInputs`.

### 4. A poll that fails to post still uses up the day's allowance (medium)
The daily creation limit (10) is charged before the poll is validated or posted.
Combined with #3, ten attempts at an NPS poll lock a person out of creating any
poll for a day, with the message *"Rate limit: You can create a maximum of 10
polls per day"*. It applies equally to a poll that goes nowhere because the bot
was not invited to a private channel. Test: *a poll that fails to post does not
use up…*.

Fix: charge after the poll has posted somewhere, or give the charge back on
failure (the DM allowance already does this: `claimNotification` and
`releaseNotification`).

### 5. A closed poll gives its creator no way to export from the channel (medium)
The More button (#11) is only on active polls, so after Close the message offers
View Results and Send, and the creator's Export is gone from where they were
reading. The More screen already handles closed polls (it hides Close and keeps
Export), so this is a gap in how it was wired, not in the screen. Test: *a closed
poll's message still gives its creator a way to export*.

### 6. `/poll-export` fails in most public channels (medium)
The command uploads the file into the channel it was typed in. Slack lets the
bot *post* to a public channel it has not joined, but not *upload* to one, so the
command fails with a raw `An API error occurred: not_in_channel` unless the bot
was invited. The Export buttons (More, `/polls-list`) already avoid this by
sending the file to the creator's DM; the slash command should do the same.
Test: */poll-export works in a public channel the bot has not joined*.

### 7. A poll can be created with a close time in the past (low)
It posts as an active poll and closes at the next sweep or the first vote.
Nothing says why. Reject it on the Options screen with an inline error. Test: *a
poll cannot be created with a close time that has already passed*.

### 8. The first press after the bot sleeps always fails (medium, verified)
With a database slow enough to eat Slack's three seconds (a cold start), **More**
and **Vote** cannot open and the person is told to press again. The message is
kind and accurate, but the person has still done the thing twice. Slack's
guidance is to open the screen first and fill it in after: open a "Loading…"
modal immediately (no database call), then `views.update` it with the real
content. Only the *pressed* button needs the trigger; the slow work does not.
(Covered by the passing test *a sleeping database costs the first press its three
seconds…*, which documents today's behaviour. Change it when this is built.)

## Found by reading, not by running

### 9. "Co-creators" can never exist
`coCreators` is always `[]` at creation and nothing adds to it, yet the README,
the permission checks, the More screen's wording and the lists all talk about
co-creators. Either build how to add one or take the word out; right now it
promises a feature that is not there.

### 10. Anyone who can see a poll can send it anywhere
*Send to another channel* is open to every member by design (README). A poll in a
private channel can therefore be posted to a public one, with its current tally
and voter names, by any voter. It is capped at ten places an hour per person. If
private-channel polls are meant to stay private, Send needs to be limited to the
people who run the poll or to channels the sender can already read.

### 11. Limits reset whenever the bot restarts
The creation, share and DM allowances are kept in memory. A restart or a wake from
sleep gives everyone a fresh allowance, and a second instance would double them.
Fine on one always-on instance; worth knowing before scaling.

### 12. A closed poll can still be edited
`/poll-edit` changes the title of a poll after its final results were posted
under the old one. Probably worth refusing on closed polls.

## Checked, and fine

Pinned by passing tests in `test-sim.js`:

- Twenty-five people voting at once lose no votes, and the message matches the
  database (row locks work).
- A vote racing a Close is either counted in the final results or refused, and
  results are announced once; pressing Close twice announces once.
- Votes after the close time are refused and the poll closes with results posted;
  the sweeper closes, updates and announces overdue polls.
- Vote changes off, anonymous polls, hidden results (on the message and on More).
- A voter cannot reach Close, Export or Edit through More, the lists, the
  slash commands, a stale Close button, or a replayed action.
- Close with votes asks first and ends the whole screen stack.
- A private channel the bot is not in: the poll is saved and the creator is told
  exactly how to fix it. A poll sent to a person also gives its creator a copy.
- Send reports partial failure and refuses a channel the poll is already in.
- Every handler on the voter and creator paths acks exactly once.
- The poll builder works from `/newpoll` to a posted poll.

## What the simulation cannot tell you

- How Slack *renders* anything (the previewer approximates it), or Slack's own
  rate limits and outages.
- OAuth install, Enterprise Grid, the `/health` route, and Render's behaviour.
- Real timing. The fake database advances a clock instead of waiting, so "a
  database that takes four seconds" is exact, but real network behaviour is not.
- Anything that needs a SQL statement the fake does not know. Unknown SQL throws
  loudly (`fake-pg: unsupported SQL…`) so a new query cannot pass unnoticed.

## Running it

```
npm test               # everything, including the simulation
node --test test-sim.js
```

`sim/harness.js` is the entry point: `const sim = await boot()`, then
`sim.user('U1').command(...)`, `.press(...)`, `.submit(...)`, and read back what
Slack would have shown. People can only press buttons that are on what they are
looking at; pass `{ forge: true }` to replay an action the screen never offered.
